# 「AI政策通」问答智能化设计

> 版本 v0.2 ｜ 2026-08-23 ｜ 由 P3 提出
> 一句话：**先判断"用户问的是哪类问题"，再决定回答结构**，而不是所有问题一律套 5 段模板。
> 实现进度：类型 2+3+4+5 已上线（2026-08-22）；**类型 6 多轮追问已实现（2026-08-23，后端驱动，前端零改动）**。

---

## 一、背景：现在的问题

`ask` 云函数当前用一条固定 SYSTEM_PROMPT，强制所有回答按 5 段结构组织（谁能办 / 要什么条件 / 怎么办 / 交什么材料 / 注意）。

这导致两类常见场景答非所问：

| 场景 | 用户真正想问 | 现在的行为 |
|---|---|---|
| 追问政策**文件本身** | "这文件哪个部门发的？文号多少？有效期到什么时候？原文链接发我" | 套 5 段模板，不直接回答 |
| 报**自身情况** | "我外地户口来广州 6 年交满社保，孩子今年升初一，能积分入学吗？" | 泛泛套 5 段，不判断"我符不符合" |

**根因**：模型没有"先判断问题类型"这一步，只有一套回答结构。

---

## 二、问题类型分类（6 类）

| # | 类型 | 典型问法 | 判定信号 | 回答结构 |
|---|---|---|---|---|
| 1 | 政策内容问答 | "创业补贴怎么申请？" | 无特殊信号 | **5 段模板**（唯一适合模板的） |
| 2 | 来源/元数据问答 | "这文件哪个部门发的？""文号多少？""什么时候实施？""原文链接发我" | 文号/部门/日期/链接/替代 | **直接回答元数据** |
| 3 | 个人情形问答 | "我外地户口来广州6年…能积分入学吗？" | 我/孩子/爸妈 + 具体事实 | **逐条对照用户情况判断** + 简短办理要点 |
| 4 | 单点事实问答 | "咨询电话多少？""在哪办理？""要交哪些材料？" | 电话/地点/材料/时限 | **一两句话直接答** |
| 5 | 比较问答 | "积分入学和积分入户有什么区别？""能同时领吗？" | 区别/对比/能同时 | **对比形式** |
| 6 | 多轮追问 | 先问"怎么入学"再问"那材料呢？" | 指代、承接上文 | 依赖 `history`（后续单独做） |

> 非政策问题（天气/房价预测等）不属于上面任何一类，继续走现有"无匹配 → 联网 → 引导 020-12345"。

## 三、分类机制：关键词规则 + 优先级

### 3.1 做法

在 `ask` 里加一个纯规则函数 `classifyQuestion(question)`，**零额外模型调用、几乎零延迟**。命中后只换回答结构，不改检索逻辑。

### 3.2 判定关键词表（初版，测试时再调）

| 类型 | 触发关键词（正则，命中即判） |
|---|---|
| **5 比较** | 区别｜对比｜有什么不同｜哪个好｜能同时｜可以同时｜同时.*吗 |
| **2 元数据** | 文号｜发文｜发布｜哪个部门｜哪个局｜哪个机关｜实施｜生效｜失效｜有效期｜截止｜到期｜什么时候开始｜何时发布｜原文｜链接｜网址｜文件名称｜文件名叫｜被.*替代｜有没有更新 |
| **3 个人情形**（只认**具体事实**，不认"我想了解一下"这类客套） | 我是.*户口｜我是广州｜我是天河｜我孩子｜我小孩｜我儿子｜我女儿｜我爸妈｜我父母｜我爸｜我妈｜我老公｜我老婆｜我今年｜我社保｜我交满｜我交了｜我交够｜我满｜我住｜我户口｜我家｜我刚毕业｜我毕业｜我年龄｜我.*岁｜老人家｜我目前 |
| **4 单点事实** | 电话｜联系方式｜在哪｜在哪里｜哪个街道｜哪个区｜地址｜什么材料｜材料清单｜需要什么材料｜多久｜多长时间｜时限｜几天 |
| **1 内容** | 其余全部 |

**排除词（命中这些不算个人情形）**：`我想了解一下｜我想问一下｜我想咨询｜我想知道｜我看看｜我想看`

> 关键取舍：类型 3 只由"我/孩子/爸妈 + 具体事实"触发。"我要申请创业补贴"没有具体事实 → 判成类型 1（5 段），避免过度解读。"我今年毕业想申请创业补贴"有"我今年毕业" → 判成类型 3，先判断适不适用再给流程。

### 3.3 优先级（多条同时命中时，谁先判谁赢）

```
比较(5) > 元数据(2) > 个人情形(3) > 单点事实(4) > 内容(1)
```

示例：
- "我和积分入户有什么区别" → 比较（"区别"优先于"我"）
- "我家人的养老咨询电话是多少" → 元数据/单点优先，个人情形其次
- "那材料呢？"（追问，无上文）→ 单点事实，给材料清单（可接受的降级，多轮上线后更准）

## 四、各类回答结构（Prompt 变体）

规则 1/2/4/5/6/7/8 各类型**共用**（只依据官方原文 / 通俗口语 / 末尾出处 / 以最新公告为准 / 本地优先 / 【信息不足】标记 + 联网兜底）。只有"规则 3（回答结构）"按类型替换。

### 4.1 类型 1 内容问答（默认，保持不变）
> 现行 SYSTEM_PROMPT 规则 3 原样保留：5 段结构，原文未提写"原文未提及"，本次不涉及写"本次问题不涉及"。

### 4.2 类型 2 来源/元数据
替换后的规则 3：
```
若用户询问的是政策文件本身的元数据（发文部门、文号、实施/生效日期、失效日期、
有效期、原文链接、文件名称、是否被新文件替代等），直接逐一回答这些问题；
原文未收录的信息如实写"未收录"，不得编造文号或日期。
```
> 数据基础：检索出的每篇原文已带 meta（标题/文号/来源/链接/发布日期），模型直接从中取，取不到就"未收录"。这正好和路线图"文号补全"联动——文号补得越全，这类问题答得越好。

### 4.3 类型 3 个人情形（**本次重点**）
替换后的规则 3：
```
用户提供了自身具体情况（如户籍、来穗年限、社保、年龄、子女情况等）。
请逐条对照官方原文判断：
  ① 明确符合条件的信息 → 明确说"你符合"，并引用原文依据；
  ② 原文未写明、无法替他确认的信息 → 明确说"这一条原文未明确，
     建议向 020-12345 或相关部门确认"，不要替用户下结论；
  ③ 明显不符合 → 明确告知差在哪一项。
判断之后，用简短一段补充"怎么办 / 要什么材料"的要点即可，
不要重复整篇政策的完整结构。
```
**要点**：这是评审最想看的能力——AI 不是复读政策，而是**把政策套到用户身上判断"我能不能办、差在哪"**。回答长度也短于 5 段，更抓人。

### 4.4 类型 4 单点事实
替换后的规则 3：
```
若用户只询问单一信息点（咨询电话、办理地点、所需材料、办理时限等），
用一两句话直接给出，不要展开成完整结构。
```

### 4.5 类型 5 比较
替换后的规则 3：
```
若用户询问两项政策/两种方式之间的区别、或能否同时享受，
用对比形式分点回答：相同点、不同点（或能否同时）、各自向谁申请。
```

### 4.6 类型 6 多轮追问（已实现 2026-08-23，后端驱动，前端零改动）

"那材料呢"这类短句追问不再丢上下文。做法：

1. `ask` 内部按 OPENID 查 `conversations` 最近 1 轮（`loadRecentHistory`，不 orderBy、内存排序，避免建索引），**前端不用传 history、不用改任何代码**。
2. `isFollowUp(question)` 纯正则判定追问：**短句（≤15 字）+ 强指代/承接词**（那/这/它/上面/刚才/之前/然后/还有/具体/呢）。只认强信号，避免把"咨询电话是多少""我想了解一下积分入学"这类独立问题误判成追问。
3. 判定为追问时：**检索用"合并问题"** = `上一轮问题 + " " + 当前问题`（如"积分入学怎么办理？ 那材料呢？"），让向量检索回到上一轮政策话题；Prompt 附 `【对话上下文（上一轮）】`（用户上一轮问题 + 回答前 400 字），并提示"主依据仍以本次检索到的政策为准"。
4. 分类仍在**原始问题**上做（type 日志显示用户实际输入，便于调关键词）。

## 五、边界情况与防误判

| 输入 | 期望判定 | 处理 |
|---|---|---|
| "我想了解一下积分入学" | 类型 1 | "我想了解一下"在排除词里，不触发类型 3 |
| "我要交什么材料？" | 类型 4 | "材料"触发单点；"我交"需写成"我交满/我交了/我交够"，避免误判成个人情形 |
| "我在哪里办积分入学？" | 类型 4 | "我在哪里"不匹配"我在广州/我在天河"式个人事实，正常判单点 |
| "我要申请创业补贴"（无具体事实） | 类型 1 | 无"我是/我今年/我交满"等事实 → 5 段 |
| "我今年毕业想申请创业补贴" | 类型 3 | 有"我今年毕业"事实 → 先判断适不适用 |
| "文号是多少？" | 类型 2 | 命中"文号" |
| "那材料呢？"（追问） | 类型 4 | **多轮追问已上线**：合并上一轮问题再检索 + 带上下文，能正确接到上一轮政策 |
| "这个政策被新文件替代了吗？" | 类型 2 | 命中"替代"；当前数据无 `superseded_by` → 如实说"库中未标注，以官网最新公告为准" |

## 六、实现方案（ask 云函数改动）

不改检索、不改联网兜底、不改熔断。只加一个分类函数 + 按类型换 Prompt。

```
改动前：SYSTEM_PROMPT(固定) + buildPrompt(固定) → 生成
改动后：classifyQuestion(question) → type
        → 选 SYSTEM_PROMPT 变体 + buildPrompt 的 structureLine(type)
        → 生成（其余逻辑原样）
```

具体步骤：
1. 新增 `classifyQuestion(question)`：正则按"比较 > 元数据 > 个人 > 单点 > 内容"顺序判断，返回 `content/meta/personal/fact/compare`。
2. 新增 `TYPE_PROMPTS`：5 个 SYSTEM_PROMPT 变体（公共规则复用，规则 3 替换）。
3. `buildPrompt` 增加 `type` 参数，把 5 段那一行换成 `structureLine(type)`。
4. 主流程里 `const type = classifyQuestion(question)`，传给生成与 buildPrompt；其余（向量检索、拉原文、联网、熔断、source 去重）一律不动。
5. 加一行日志 `console.log('[ask] type=' + type)`，预览 Console 里即可核对分类是否正确，方便调关键词。

> 延迟影响：分类是纯正则，耗时可忽略。5 段 → 变体只影响 Prompt 文本，不增加调用。

## 八、优先级与风险

### 8.1 排期建议
| 优先级 | 内容 | 状态 |
|---|---|---|
| P0 | 类型 2 + 3 + 4（元数据 / 个人情形 / 单点事实） | ✅ 已实现（2026-08-22） |

| — | 类型 1（回归） | ✅ 23 条分类用例全过（含 3 条边界修正） |

### 8.2 风险与对策
- **5 段回归**：只按类型换 Prompt，默认仍是内容类 → 把第 1/15 条回归用例跑通再部署。
- **个人情形误判**：靠排除词 + "只认具体事实"缓解；用预览 Console 日志逐个核对分类。
- **编造元数据**：类型 2 明确"未收录如实说"，配合路线图文号补全越补越好。
- **别一次做太多**：先上 2+3+4 验证稳定，再加 5；8/31 红线优先于一切炫技。
